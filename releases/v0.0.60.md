# pain001-loader-mt101 v0.0.60

Version-alignment release. This package joins the suite's single version
line, moving from `0.0.2` to `0.0.60` to match `pain001` and every other
member. No public API change and no change to the MT101 → pain.001
mapping.

## Why the jump

Every package in the [`pain001`](https://github.com/sebastienrousseau/pain001)
suite now ships the same version number: the core, `pain001-mcp`,
`pain001-lsp`, `pain001-loader-xlsx` and this package. If the core is at
`0.0.60` then so is everything else, so there is never a compatibility
table to consult.

This package had been numbered on its own line, reaching `0.0.2` while
the core reached `0.0.60`. Both numbers were defensible under the
previous policy, which versioned loaders independently — but a user
looking at `pain001-loader-mt101 0.0.2` next to `pain001 0.0.60` had no
way to tell whether that was intentional or drift. Catching up in one
step removes the question permanently.

The jump skips no work: `0.0.3` through `0.0.59` were never released for
this package and never will be. Versions advance in `0.0.1` steps from
here, staying on the `0.0.x` line — `0.1.0` follows `0.0.999`.

## What changed

- `0.0.2` → `0.0.60`.
- Benchmarks and a scaling guard (`tests/test_benchmarks.py`), run in CI
  with results kept as an artifact. The guard compares the parser
  against itself at two sizes rather than using a wall-clock threshold,
  so it does not depend on how fast a runner happens to be.

The `pain001 >= 0.0.55, < 1` floor is unchanged; nothing here needs a
newer core.

The public surface is unchanged — a single function:

```python
from pain001_loader_mt101 import parse_mt101

rows = parse_mt101(swift_message_text)
```

## Verification

- 46 tests, 100% branch coverage, 100% docstring coverage
- Benchmarks: parsing is linear (2.00x and 1.86x per doubling across
  1000 → 2000 → 4000 transactions)
